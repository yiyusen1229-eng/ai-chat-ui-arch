## 现在的污染点在哪里

刚做的群聊是“最小版”，实际只接了三样东西：

| 环节 | 现在用的 | 问题 |
|---|---|---|
| 人设 | **当前角色**（`persona_ctx.persona_text`） | 雪菜说话时，用的还是和纱的人设 → 只能靠模型凭名字猜，必 OOC |
| 记忆书 | **当前角色**（`_memory.runtime()`） | 其他角色完全没有自己的记忆可注入 |
| 历史 | 当前角色的 `sessions/<slot>.json` | 群聊记录写进和纱的存档；换成雪菜当主角，她的存档里没有这段 |

所以真正的问题不是“串味”，而是**只有一个人的大脑在替所有人说话**。串味是下一步的事：等雪菜有了自己的私聊记录，如果把这些私聊记录也喂给群聊，才会真正互相污染。

## 三个可选方案

**A. 场景化存档（推荐，改动中等）**

```

scenes/<scene_id>/log.json      ← 公共：参与人 + 全部台词
characters/<id>/memory/         ← 私有：只由"她在场的场景"生成
characters/<id>/relations.json  ← 私有：她对其他人的态度
```

- 每一轮只调用一次模型，只调用**发言者**的视角：`发言者人设 + 发言者私有记忆 + 公共最近 N 轮 + 关系块`
- 谁说话就换取谁的人设和记忆 → 解决 OOC
- 记忆摘要在场景结束后按参与人分发给各自记忆书 → 不串味
- 单角色对话 = 参与者只有一人的场景，旧存档可迁移

**B. 逐条可见性标记**

每条消息带 `visible_to: ["和纱"]`，支持“耳语/私聊”。代价：裁剪要按视角做，逻辑复杂；群聊里默认 `all`，只有特殊剧情才用。

**C. 只做摘要隔离（最省事）**

公共区的最近 K 轮原文照旧放进上下文，**不摘要**；各角色记忆书只从“她在场”的对话里长。改动最小，但长场景 token 会涨。

## 我建议的落地顺序

1. **先 A 的骨架**：`scenes/` 存档 + 发言者视角注入 + 记忆按参与人分发。（这是主干，1 次到位）
2. **再关系网**：`relations.json` 里一句话态度，说话时注入“你对面这个人，你现在是敌视/别扭”。成本极低，效果立竿见影。
3. **最后 B**：只在需要“背着某个人说话”的剧情里用可见性标记。

## 几个需要你拍板的点

1. **存档结构**：`scenes/` 是新目录，和现有 `characters/<id>/sessions/` 并存还是替换？我倾向**并存 + 迁移**（旧档读一次自动包成单人场景），不改现有存档格式，风险最低。
2. **谁决定下一个说话的人**：现在交给模型（它偶尔自己加人，比如刚才冒出雪菜）。要不要加约束——**只能从已选同场角色里挑**，超出就不允许？
3. **记忆分发**：群聊结束后，是否要按“每个角色各自视角”分别总结一份（贵一点，但最干净）？还是只把群聊日志当公共历史，**不写进任何人的记忆书**（省钱，但角色会“忘”）？
4. **语音**：其他角色要不要也配音？这取决于你是否有雪菜的参考音频放进 `characters/雪菜/voice/`。

## 一、三层结构

```
         ┌────────────────────────────┐
  玩家 → │  导演 Director（全局唯一）  │ ← 玩家设：本段跨度 N 轮 + 大致走向
         └────────────┬───────────────┘
                      │ 输出「分镜」而不是散文
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
   旁白/特写      角色A的LLM     角色B的LLM
   （导演自己写）（各自角色包）   （各自角色包）
                      │              │
                   语音A          语音B（可选）
```

关键点：**导演不写台词，角色不做调度**。

- 导演输出「这一拍由谁、以什么方式、说什么方向」
- 角色模型只拿到「你这一句要说什么」，用自己的人设+记忆+模型写出来

这样每个角色的模型都很“窄”，OOC 概率大幅下降，也天然不会互相抢话——因为 A 根本不知道 B 要说什么。

## 二、导演的输出应该是什么样（契约）

不能让导演写散文，必须给它一个窄接口，比如：

```json
{
  "beats": [
    {"type": "narr",  "text": "教室里只剩两个人的呼吸声。", "camera": "close"},
    {"type": "say",   "who": "和纱", "intent": "嘴硬，但声音在抖", "len": "short"},
    {"type": "say",   "who": "雪菜", "intent": "试探，装作没听懂"},
    {"type": "think", "who": "和纱", "text": "（……为什么她偏偏这时候来）"}
  ],
  "budget_spent": 2,
  "next_beat_hint": "把冲突压到临界点但不爆发"
}
```

有了这个结构，"出旁白/给特写/心理描写/独白/回忆"就都变成 `type` 的不同取值，而不是靠提示词求模型自觉。

## 三、节奏控制：跨度 × 详略

你说的“七八轮写很大跨度 = 略写”，本质是一个**预算**问题。我建议显式做成：

```
本段预算 B = 玩家设的轮数（或"分钟""字数"，见问题2）
每拍扣预算：narr 扣 0.3，say 扣 0.5，think 扣 0.3，skip 扣 N（一次性略过）
导演每拍必须回答：这一拍之后，"局面"发生了什么不可逆的变化
```

- 预算快耗尽（<20%）→ 提示导演“该收束了”，它倾向输出 `skip` + 一段总结
- 预算宽松 + 局面没变化 → 检测“原地打转”的导演（连续两拍 `next_beat_hint` 语义相同就警告它推进）

**“草草略写”不是靠模型猜，而是让它显式地花预算**。这样“废话绕圈子”也能被预算机制压住：绕圈子不消耗局面变化，但消耗预算，玩家会立刻感觉到“这段没内容”。

## 四、玩家随时插话，这是最难的一块

我建议把玩家输入当成**最高优先级事件**，走“中断-重规划”：

```
导演持有剧本状态：{当前幕, 已花预算, beats队列, 悬念/待解决清单}
玩家插话 → 立即：
  1. 停掉正在播的语音与预生成队列（现在的 wt-auto 已有中断能力）
  2. 把玩家这句话交给导演，让它 re-plan（不是作废，是重排）
  3. 保留已花预算与未解决悬念
```

两档模式：

| 模式 | 行为 |
|---|---|
| 自动（现在这个） | 导演自驱，一直演到预算耗尽或出现选择支 |
| 半自动 | 每演 N 拍停下等你，像 galgame 的“章节” |

你说的“用户随时插话”在半自动里是自然的；在自动里就是上面那套中断-重规划。

## 五、多模型并存的工程问题（比想象的多）

1. **配置落点**：每个角色包一个 `model.json`（provider/model/key/temperature），语音一个 `voice.json`。导演自己也一份。
2. **失败回退**：某角色模型挂了 → 回退全局默认模型，并标记“这句是降级生成的”，否则整场戏卡死。
3. **成本**：一轮群聊 ≈ 导演 1 次 + 说话角色 1 次（narr/think 由导演写，不额外调用）。所以比现在贵 ~2 倍。可以让**导演用便宜模型**（它只做调度，不需要文采）。
4. **延迟**：导演 → 角色 是串行两次调用，一句台词可能 3~6 秒。现在的“预生成 3 条缓冲”正好能吃掉这个延迟，架构上不用改。

## 六、上下文怎么切（接上次的隔离方案）

每个角色模型只看到：

```
她自己的人设 + 她自己的记忆书 + 她对在场者的态度
+ 公共最近 K 轮（原话）
+ 导演给她的这一拍任务：「你现在要说的是：嘴硬但声音在抖，短句」
```

**不给她全剧本**。这是防 OOC 和防抢戏的核心。

1. **导演写不写旁白？** 我倾向让导演直接写（省一次调用），但文采取决于导演模型。

3. **玩家插话后**：已花预算保留（偏真实）还是清零重算（偏宽松）？
4. **角色能不能看见玩家最新一句**：看得见但由导演决定谁接（我倾向这个），还是只在被点名时给？
5. **成本上限**：要不要给每场设“最多 N 次调用/元”的硬闸？

## 助手

不写代码，把这个分工问题谈清楚。你说得对：**导演必须写剧本，但绝不能写台词**，否则角色模型确实就废了。这两件事是不同层次。

## 一、四层，谁拥有什么

| 层 | 谁负责 | 产出 | 角色AI能看到的 |
|---|---|---|---|
| **剧本层** | 导演 | 本段目标、张力曲线、必须发生的事、预算 | ❌ 看不到 |
| **分镜层** | 导演 | 这一拍轮到谁、用什么手法（旁白/特写/独白/回忆/沉默） | 只看到“轮到我” |
| **台词层** | **角色自己的模型** | 具体说什么、语气、心里怎么想 | ✅ 这是它的活 |
| **叙述层** | 导演（或叙述者模型） | 环境、动作、氛围 | — |

关键：导演给角色的是**任务**，不是台词。

```
导演 → 和纱：「现在雪菜刚说了句试探的话，你要嘴硬但露出破绽，短句，不要正面回答」
和纱（自己的模型）→「……别问了。跟你没关系。」
```

角色模型完全自由发挥“怎么说”，但逃不出“这一拍要发生什么”。

## 二、角色之间互相影响，怎么安排

你担心的这点，答案不在“让角色互相读心”，而在**顺序 + 可观察行为**。

小说里人物本来也读不到对方内心，只能看到对方说了什么、做了什么表情。所以：

```
一拍 = 一个"回合"，内部按导演给的顺序串行：

  和纱行动（她看到：公共上文 + 本轮已发生的事）
     ↓ 她的输出写入公共区（台词 + 动作）
  导演判断：谁该接？（可以是一次很轻的路由）
     ↓
  雪菜行动（她看到：上文 + 和纱刚才说了什么，但**看不到和纱的内心**）
     ↓
  导演判断：这一拍够了吗？还差一个旁白收尾吗？
```

**不是**让 A 和 B 同时生成再拼接，而是 A 说完，B 基于 A 的**外部表现**反应。这就是“互相影响”的真实机制，也顺便把“串味”问题解决了一半：角色之间共享行为，不共享内心。

## 三、导演和角色的调用节奏（成本关键）

如果每拍都问导演一次，一轮 2~3 个角色 = 3~4 次调用，太贵。建议：

```
导演：一次规划 2~3 拍（batch），输出 beats 队列
      ↓
执行：拍1(和纱→雪菜→旁白) → 拍2(...) → 拍3(...)   ← 中间不再问导演
      ↓
例外：角色说出"意外内容"（超出导演预期）时，才插一次重规划
```

- 导演调用：**每 2~3 拍 1 次**
- 角色调用：每个角色每次发言 1 次
- 路由（谁接话）：**优先用规则**（被点名者优先、没说话的人优先、上次说的不连说），规则拿不准才问导演

这样 3 人对话一轮 ≈ 2~3 次调用，和现在差不多。

## 四、怎么防止角色“照着剧本演”

最重要的约束：**角色看到的不是导演的完整计划**，只有：

- 她自己的人设 / 记忆 / 对在场者的态度
- 公共最近 K 轮（别人说的原话）
- **一句**本拍任务（“你要嘴硬但露破绽”）

不给她“接下来会爆发争执”这种未来信息。否则她会提前演结局，戏就假了。

## 五、导演的输出契约（示意）

```json
{
  "arc": "剑拔弩张 → 争执爆发",
  "beats": [
    {"goal": "试探", "tension": 0.4,
     "order": [{"who": "雪菜", "task": "装作随口一问，其实在确认"},
               {"who": "和纱", "task": "把话题挡回去，语气比平时冲"}]},
    {"goal": "擦枪走火", "tension": 0.8,
     "order": [{"who": "和纱", "task": "被戳中，音量上来"},
               {"type": "narr", "text": "……"}]}
  ],
  "budget_spent": 2
}
```

`type: "narr"` 由导演自己写；`who` 由角色模型写。

## 六、“用小说原本训练导演”

这是对的，而且是这个方案最有价值的部分——但分成两档：

- **现在（提示词级）**：把小说原文当风格样本 + 少样本示例塞给导演，成本最低
- **以后（微调）**：训练数据就是「(已有上文, 玩家给的框架) → 分镜 JSON」。小说原文本身不直接能用，得先转成这个格式；这一步才是“整理素材”的实际工作量

也就是说：**小说是语料，但训练目标不是“写小说”，而是“把一段上文 + 一句框架，拆成可执行的分镜”**。这个转换脚本才是要写的东西。

## 七、需要你确认的四件事

1. **导演写旁白吗？** 我倾向让导演写（它有全局视角，旁白就是它的“镜头语言”）。角色模型只负责台词和内心。
2. **一个角色在一拍里能行动几次？** 我倾向 1 次（说完就换人），否则容易出现独白过长。
3. **角色要不要看到“上一拍导演给别人的任务”？** 我倾向**不给**——只给她自己那条。
4. **玩家插话的优先级**：立刻中断当前拍、保留已花预算、让导演从“现在”重排（我倾向这个）。

这四点你点头，我就能把导演的 JSON 契约和调用时序定死，再动手。

## 用户

有的时候一个角色可能做出一连串的行动，而另一个角色保持沉默或者不做行动，所以一拍里只让行动一次明显不太合理，这个要由导演来动态安排。但是还有一个最大的问题，剧请给出来后，每个角色会对当前上文产生不同的反应，而它们各自的反应又都会影响彼此的反应，就是说它们不是一个时态上的先后而是并行相互影响的。比如在开启多角色对话后的第一轮，ab角色同时产生了反应，这个时候a先行动了，b就会对a的行动结合上下文产生不同的新的反应，从而反应变化了，就是人类说话的时候会因为环境的变化而想法不断变化，就是这个意思。


## 助手

这个点很关键，而且它直接决定架构。你说的“并行相互影响”，如果按“你说一句、我回一句”的串行模型来做，**永远做不出来**。得把“反应”拆开。

## 一、反应不是一句话，是三层

| 层 | 是什么 | 谁生成 | 何时生成 |
|---|---|---|---|
| **立场 stance** | 此刻她想要什么、情绪、戒备程度、她打算做什么 | 角色自己的模型 | 局面**实质变化**时（一拍开始时） |
| **增量 delta** | 听到别人这句话后，“我刚才的想法要不要改” | 角色自己的模型 | 每次别人行动之后（一句话） |
| **表达 utterance** | 真正说出口的台词 / 做出来的动作 | 角色自己的模型 | 轮到她行动时 |

关键：**“并行”发生在 stance 层，不是台词层。**

```
t0  导演给出局面
    ├─ 和纱 stance：想追问，但怕暴露        ← 并行生成
    └─ 雪菜 stance：装作不在意，其实在听    ← 并行生成

t1  导演让和纱先动
    └─ 和纱 utterance：「……你们俩，最近很奇怪。」

t2  雪菜收到"和纱说了这句" → delta：「她果然察觉了 → 从'装傻'改成'先发制人'」
    └─ 雪菜 stance 更新（只改一句话，不重写整个人设）

t3  导演让雪菜动
    └─ 雪菜 utterance：「奇怪的是你吧？」

t4  和纱 delta：被反将一军 → 戒备↑
```

她的“想法因环境不断变化”就体现在 **delta 累积**上，而不是每次都重新生成一个人。

## 二、一次“拍”里能有几个动作，是导演的事

```
beat = {
  goal: "擦枪走火",
  tension: 0.8,
  seq: [
    {who: "和纱", budget: 2},      ← 她可以连说两句（对方沉默时）
    {type: "narr"},
    {who: "雪菜", budget: 1}
  ]
}
```

- 角色连说 2 句时，每句之间**其他人都会收到 delta**（哪怕不出声）——这就是“沉默的一方其实在变化”
- 沉默但不空转：delta 可以产出“无声反应”（皱眉、别过脸），由导演决定要不要写成旁白

## 三、真正的“同时”——overlap

有时就是同时发生，比如两人同时开口、打断。导演可以标：

```json
{"who": "和纱", "overlap": true}
{"who": "雪菜", "overlap": true}
```

带 `overlap` 的几句 **都基于同一份 snapshot 生成**，互相看不到对方这句。结果就是抢话、撞话、话说一半被打断——小说里最有张力的部分恰好来自这里。

这比“并行模拟”便宜得多：只是并行发两次请求，不需要多轮迭代收敛。

## 四、防“来回震荡”

并行+增量最大的风险是：A 一句、B 一句、A 再一句……永远不收敛（绕圈子）。

三道闸：

1. **张力曲线**：导演每拍给定张力值，delta 只能让张力往曲线方向走，不能自己乱涨
2. **预算**：整段有轮数预算，每拍扣
3. **settle 规则**：连续 2 次 delta 后“局面没有任何不可逆变化”→ 强制导演推进（换场景、抛出事件、或 `skip`）

## 五、成本与延迟（这是能不能落地的关键）

| 环节 | 调用 | 能不能并行 |
|---|---|---|
| stance（一拍开始，所有在场角色） | N 次 | ✅ 各自模型，天然并行 |
| utterance（每个动作） | 1 次 | 串行（要看到前一个动作） |
| delta（别人行动后，受影响的人） | 0~N 次 | ✅ 并行，且输出极短（一句话） |

一拍 2 人 ≈ 2(stance 并行) + 2~3(utterance) + 2(delta 并行) ≈ 但**时间上**大约 2 个串行往返，不是 6 个。加上现在已有的“预生成 3 条缓冲”，播放时几乎感觉不到等待。

省钱要点：**delta 用最便宜的模型**（它只输出一句话，甚至可以让导演兼任）。

## 六、落点（不写代码，只说结构）

```
character runtime（每个角色一份）
  ├ stance：当前意图/情绪/戒备（随 delta 更新）
  ├ memory：私有记忆书
  ├ relations：对在场者的态度
  └ observable：她*看到*的公共行为流（不含别人内心）

director
  ├ arc：玩家给的大致框架
  ├ beats：分镜队列（who/type/budget/overlap）
  ├ budget：剩余轮数
  └ blackboard：当前局面摘要（张力、未解决的事）
```

两个必须守住的红线：

1. **角色只看到别人的“行为”，看不到别人的“内心”** → 天然避免串味，也符合小说真实感
2. **角色只拿到自己那条任务**，不给她全剧本 → 不会提前演结局

## 需要你点头的三件事

1. **stance 层要不要真的并行生成？** 代价是一拍开头多一次并行往返（约 +1 秒），换来“同时产生反应”的真实感。
2. **delta 由谁算？** 我倾向让**导演兼任**（它掌握全局，且能顺便判断张力），省一次角色调用。
3. **沉默角色要不要产出“无声反应”**（皱眉/别过脸），写进旁白？这会让戏更像小说，但旁白量会增加。

这三点定了，导演的 JSON 契约就能定死（stance / beats / delta / overlap 四类消息），我再动手。

## 用户

其实我觉得最好的方案，还是由导演来告诉各个ai已经写好的剧本，他们该在哪一拍说出大致什么样的内容，做出什么样的演出，只是具体内容由角色自己生成，这样就很好处理了。但是那样的话由于不可能把每个角色的角色包都塞给导演，那样等于又让一个ai同时扮演多个角色了。但不那样的话，因为导演没有那些资料，就很可能写出ooc的剧情。


## 助手

你抓到的正是这个架构的真正难点：**导演知道的越少，越容易写出 OOC 剧情；知道的越多，就越会自己演，角色 AI 也就变成摆设。**

这是一个信息接口问题，解法不是“给不给”，而是**给什么形态**。

## 一、导演不该拿到“角色包”，该拿到“角色卡”

两者区别：

| | 角色包（角色模型用） | 角色卡（导演用） |
|---|---|---|
| 体量 | 几千字人设 + 世界书 + 记忆书 | 150~300 字 |
| 内容 | 完整经历、口癖、关系史、禁忌 | 性格 3 条、说话方式 3 条、**当前**关系态度、**绝不会做**的事 |
| 谁生成 | 用户/原作 | 一次性由角色包压缩出来，之后可手改 |

导演看到的是卡，不是包。这样：

- token 可控：3 个角色卡 900 字，完全可以塞
- 不会替角色写台词：卡里没有台词素材，只有约束
- OOC 概率大降：卡里明确写了“绝对不会主动示弱”这类红线

## 二、导演写的不是“台词内容”，是“这一拍要发生什么 + 红线”

对比一下两种写法：

```
❌ 导演写内容（容易 OOC）
   和纱：「我才不在乎你去不去呢，反正我也很忙。」（话里带着明显的失落）

✅ 导演写约束（角色自己写词）
   和纱：嘴硬、否认在意、把话题推开；不要示弱、不要道歉；2 句以内
        → 角色模型：「……别自作多情了。我本来就没打算去。」
```

**导演负责“发生什么”，角色负责“怎么说”**。你担心的“导演写 OOC”，很大程度上是让它写台词造成的，而不是它不懂角色。

## 三、不确定的时候，导演可以“问”角色

这是缺的那块拼图：导演不需要背角色包，它只需要**能查**。

```
导演：{ 咨询: "和纱", 问题: "雪菜提到三年前的演唱会，你会怎么反应？一句话。" }
和纱模型（带完整包）："……别提那件事。"
导演据此决定：这一拍让和纱沉默，改由雪菜继续推进
```

特点：

- 这是一次**很短的调用**（输出一句话），不是完整回合
- 每拍最多问 1~2 次，只在导演“拿不准”时问
- 因为回答问题的是角色自己的模型（带完整包），所以答案一定符合人设

成本上大约每拍 +0.3 次调用，换来“导演永远不会写出角色不可能的反应”。

## 四、事后还有一道闸：角色可以拒绝

角色生成的时候，除了台词，还要让它顺带返回一个自检：

```json
{"line": "「……别自作多情了」", "comply": true}
{"line": "「对不起，我错了」", "comply": false, "why": "她不会主动道歉"}
```

- `comply: true` → 直接演
- `false` → 把 `why` 回给导演，让它改这一拍的任务（一次）

这一步几乎不花钱（同一次调用的附带输出），但能兜住导演的误判。

## 五、四种方案对比

| 方案 | 导演 OOC 风险 | 角色 AI 是否浪费 | token | 结构风险 |
|---|---|---|---|---|
| 全包灌给导演 | 高（它会自己演） | **是** | 爆炸 | 高 |
| 只给导演节拍（不给卡） | 中 | 否 | 低 | 剧情松散 |
| **卡 + 按需咨询 + 自检** | 低 | 否 | 可控 | 低 |
| 导演完全放手 | 低 | 否 | 低 | 容易变成流水账 |

我推荐第三种，它是唯一同时满足“导演写得了像样的剧情”和“角色 AI 不被架空”的方案。

## 六、这套下来，工作量在哪儿

真正要写的不是对话循环，而是三个“压缩/校验”部件：

1. **角色卡生成器**：从角色包压出 200 字卡（一次性，之后可手改）
2. **导演的调度契约**：beats（who / 任务 / 红线 / 张力 / overlap）
3. **咨询与自检通道**：两个短接口，前者导演问、后者角色答“我做不到”

对话主循环反而是最简单的部分——顺序执行 + delta 更新（上一轮讨论过）。

## 需要你定三件事

1. **角色卡谁写？** 我建议程序从角色包自动压一版，你再手改——比纯手写省事，也比纯自动准。
2. **导演能不能“咨询”角色？** 这是解决 OOC 的关键，但会让导演多一次依赖。允许 / 只在拿不准时允许 / 完全不给。
3. **角色自检 `comply:false` 时怎么办？** 我建议：回给导演改一次；还不行就换人接话（比如让旁白带过），不能死循环。

这三点定了，我就能把导演的 JSON 契约、角色卡的字段、以及“咨询/自检”的调用时序一次写清楚。

## 用户

你说的这几个点都很好。但是有点小问题。1.拿角色卡的方案，每次多角色通常对话设定的可能都是不同的角色在场，那每次都得自动生成相应的角色卡吗？或者哦我想到了，在做角色包的时候就加一个角色卡文件夹，只在多角色对话的时候生效提交给导演。  234都很好，一起用应该能最大确保不ooc。然后我想到了，有些路人角色该怎么办呢？比如有的时候可能会和路人发生对话。这种非常驻的龙套角色，就直接由导演来根据剧情需要填话好了，毕竟也不需要有什么内涵深度，也不用语音了。


## 助手

三点都对，尤其“角色卡放角色包里、只在多角色时提交给导演”——这正好把“整理素材”变成角色作者的事，而不是运行时的事。

## 一、角色卡：同意，补三个细节

```
characters/<id>/
  card/
    director.md      ← 给导演的卡（150~300 字），只有多角色时才提交
```

**① 生成时机**：角色包做好时生成一次，之后跟着包一起改；运行时**不生成**（运行时生成会引入不确定性和延迟）。给个工具 `tools/make_cards.py`：从人设+世界书压一版，你再手改。

**② 卡要分“静态/动态”两半**：

| 静态（进卡文件） | 动态（不进卡） |
|---|---|
| 性格 3 条、口吻 3 条、**绝对不会做的事** | 当前对在场者的态度（敌视/别扭/亲近） |

态度是**每场都会变**的，写死在卡里很快就过期。动态部分从 `relations.json` 按当前场景注入，导演拿到的卡 = `静态卡 + 本场关系一行`。

**③ 卡要有“指纹”**：卡文件里记一个源包哈希。角色包改了、卡没改 → 启动时提示“卡可能过期”。不然半年后会得到一张和角色完全对不上的卡。

## 二、龙套：同意交给导演，但要圈四条边界

你说得对，路人不需要内涵，也不需要语音。但完全放开会有几个坑：

**① 台账**：同一个“店员”如果在三个连贯的拍里都出现，得是同一个人（同样的性别、语气、称呼）。所以导演的黑板上要有一份**临时演员表**：

```json
"extras": [
  {"id": "店员", "desc": "二十多岁女性，语气客气但敷衍"}
]
```

后面的拍引用 id，不再重新描述。

**② 只能“反应”，不能“推进”**：龙套不能成为剧情的驱动者，否则导演会拿路人替它讲剧情（很偷懒，也很出戏）。规则：龙套的台词只能是**对当前局面的反应/信息提供**，不能主动引发新事件。

**③ 不能知道不该知道的**：龙套可以问“你们吵架了？”，但不能说“我听说你们三年前……”——那属于角色才知道的秘密。

**④ 不进任何人的记忆书**：龙套的话只留在公共日志里。记忆摘要里最多出现“在便利店遇到店员”——不该成为角色的长期记忆。

## 三、三类角色的待遇差别（一张表定死）

| | 常驻角色 | 龙套（路人） |
|---|---|---|
| 由谁写台词 | 角色自己的模型 | **导演直接写** |
| 有无角色包 | 有 | 无 |
| 有无角色卡 | 有（进导演上下文） | 无（一行描述） |
| 能不能被“咨询” | 可以 | 不行 |

## 一、两个“自动”不是一回事

## 二、导演在自动模式下需要看到的

```

```

有了这五样，导演才可能“自己想”。

## 三、玩家没给方向时，导演怎么“自己续写”

关键在**第三项：悬念清单**。没有它，导演只能随机生成日常废话。

做法是让导演维护一张“待解决的事”：

```json
"open_loops": [
  {"id": 1, "what": "和纱还没回答要不要一起去音乐会", "heat": 0.7},
  {"id": 2, "what": "雪菜似乎察觉了两人的关系", "heat": 0.4}
]
```

每一拍它从里面挑一个推进（heat 高的优先），推进完 heat 下降；新的事件产生新 loop。这样“自己续写”就有了方向感，而不是每次重新随机。

配合张力曲线：

- 预算充裕 + 张力低 → 写日常（对话、细节、心理），慢慢加温
- 预算紧张 + 张力高 → 推进主线，用 `skip` 略过过渡

|---|---|---|

3. **玩家插话** → 立刻中断，重排

## 助手

你提的“先写大纲、按幕生成、最多领先一幕”是这轮讨论里最有效的解法，它同时解决了剧情连贯性、生成上限和存档截断三个问题。

## 一、分层：大纲 → 卷章 → 幕 → 拍

```
大纲（一句话～一段）        ← 玩家给的框架，或导演自拟
 ├ 第一卷
 │   ├ 第一章
 │   │   ├ 幕1  ← 生成单位（8~15 拍 / 约 800~1500 字）
 │   │   ├ 幕2  ← 按需生成
 │   │   └ 幕3
 └ …
```

规则：

- **大纲只写一次**，当场就生成（便宜）
- **卷/章只是结构**，可以不细写，导演在扩写某幕时才决定下一章怎么走
- **幕是真正的生成单位**：一次调用写一幕，写完就停
- 拍是播放单位，从幕里切出来

这样“一次生成 vs 接力生成”的连贯性问题就消失了，因为**每一次生成都是一个完整小段**，下一幕接着上一幕写，而不是每 40 字接一次。

## 二、缓冲上限因此变成“一幕”

你说“最多只能比画面多出一幕”，我理解成：

```
已显示到 幕2 第 5 拍
后台最多生成到 幕3 结束
幕4 及以后：只有大纲，没有正文
```

于是：

- 播放、内存、存档压力都小
- 之前讨论的“10 万字硬闸”基本用不上了（一幕通常一两千字），可以留作最后的保险
- 你说的“后台领先太多”从根上不会发生

## 三、存档：只截断“还没生成的”

```
存：大纲（含后面几卷的标题）+ 已生成的幕（正文）+ 当前播放位置
删：未展开的幕（本来就没生成）
```

读档回来，导演从当前位置**按大纲重新展开**下一幕。这跟你说的完全一致，而且有个好处：读档后的剧情不会和上次一模一样（重新展开有差异），反而像“重新演一遍”。

我唯一想确认的是：**大纲要不要存？** 我倾向存，因为它很便宜，而且保证读档后方向不偏。如果你不存，读档后导演得重新编大纲，可能会走到另一个故事上去。

## 四、自动模式：玩家也被调度

“自动模式就是玩家不输入了”，那系统的输入就只剩三样：**大纲、角色卡、当前局面**。玩家变成被写的角色之一。

这带来一个新问题：**导演写“你”的台词时，以什么为准？**

- 如果没有主角设定，导演会按“普通男主”的通用写法，可能和你的习惯差很远
- 所以需要一张**主角卡**（和角色卡同构，只是没有语音、没有立绘）
  - 性格 3 条、说话方式 3 条、绝不会做的事
  - 可以在“剧情方向”输入框旁边给个入口，写一次长期有效

有了主角卡，导演写“你”的发言才不会出戏，而且角色模型对“你”的反应也有一致的参照。

## 五、几个会踩的坑

1. **大纲漂移**：扩写某幕时导演可能越写越偏离大纲。解法：每幕写完做一次很轻的自检——“这一幕是否还在大纲的这一章里”，偏了就在下一幕拉回来。
2. **幕边界的落点**：幕要在自然停顿处切开（一场对话结束、一个决定做出），不能在争执高潮中间断。这交给导演判断，但要给它“这一幕必须在某个状态变化后结束”的硬指标。
3. **幕中途玩家插话**：当前幕剩下的拍作废，重排。会浪费一次生成（钱和时间），但比强行接着写自然。建议：插话时把“已生成未播放的剩余部分”丢弃并告知（“已重排这一幕”）。
4. **成本**：自动模式下每幕一次调用，加上角色台词（多角色模式下每个发言者一次）。一幕 10 拍、2 个角色 ≈ 12~15 次调用/幕。这个量级配合“用户自己看成本”是可行的。

## 需要你确认的四点

1. **幕的默认长度**：拍数（我倾向 8~15 拍）还是字数？

## 二、大幕的“幕内连续生成”，和“接力生成”不是一回事

你担心的连贯性问题是：

```
❌ 接力生成：每 40 字停一次，下一句不知道这一幕要走到哪
✅ 幕内分段：这一幕的目标已经定死，分 2~3 段写，每段都带着「本幕目标 + 上一段结尾 200 字」
```

区别在于**有没有幕级蓝图**。有蓝图的分段，读起来和一次写完差别很小；没有蓝图的接力才会散。

分段还有两个约束：

1. **段边界只能在自然处**：旁白/动作描述之后、不在台词的半句中间
2. **最后一段必须“收在悬念上”**：不许总结、不许把冲突解决干净（否则下一幕没法接）

## 一、跳过（点击界面 / 快进图标）

```
点击 / ⏩  → 队列指针 +1（如果后台还有已生成的行）
           → 没有已生成的行：什么也不做（不催生成）
```

这和现有的“点一下翻页”要分层处理：

```
这条还有下一页 → 先翻页（galgame 习惯）
这条已翻完     → 跳到下一条
```

## 二、跳过的语音规则（你这条最容易被误解，确认一下）

| 当前播放 | 跳到 | 行为 |
|---|---|---|
| 语音行 | **语音行** | 立刻打断，播新的 |
| 语音行 | **非语音行** | **不打断**，旧语音继续播 |
| 语音行 | 非语音 → 非语音 → **语音** | 到有语音那条时才打断 |
| 无语音 | 语音行 | 直接播 |

所以会出现“文字已经走到第 3 条，耳机里还是第 1 条的声音”，这是你要的效果。

**需要你确认**：如果用户连跳 5 条，第 1 条的语音还在播，这 5 条刚好都没有语音 → 那要等它自然播完，还是跳过超过 N 条就静音？

## 三、预合成：生成完就立刻把语音全部做出来

```
后端新增：文本一入队 → 立刻触发生成所有语音（按顺序，一次一条）
优先级：下一条要播的最高；其余按队列顺序
已经缓存过的跳过
用户跳过/中断 → 取消当前合成，重排
```

因为 TTS 是本地 GPU，一次一条串行即可；成本是电，不是钱。

配合现在的缓存（`_CACHE_VERSION` + 参数 key），合成完就是缓存命中，播放时零等待。

## 四、队列必须放后端（这条改变了架构）

你提的“已生成未播放不进回想、全部在后端”，实际上要求：

```
后端：演出队列（play queue）
  ├ 已生成未播放的行（含文本、speaker、语音是否就绪）
  ├ 播放指针
  └ 已播放的行（才进回想）

前端：只拿「当前这一条」+ 预取 1~2 条做无缝
```

好处：

- 回想只显示已播放的，天然满足你的要求
- 存档时把队列一起存下来（你之前说过缓冲区算存档）
- 预合成在后端做，前端不关心
- 跳过只是“移动指针”，不需要前端维护复杂状态

代价：要新增 3~4 个接口（取当前行 / 跳过 / 队列状态 / 预取），以及“生成器”和“队列”之间的衔接。

导演/生成器 ──写一幕──→ 队列（后端）

## 一、我理解的“队列”与“存档”

```
运行时（内存）          存档（磁盘）
├ 已显示的历史          ├ 历史（截至当前显示的那一句）
├ 已生成未显示的队列    ├ 场景/立绘/BGM/情绪
└ 播放指针              └ 不含队列

退出程序 → 内存全丢，没存就是没了
存档     → 只写到"当前显示的那一句"，后面的队列一律丢弃
```

也就是说：**队列不写进存档文件**。你前面说“队列进存档”，这句我理解为“队列属于运行时状态”，最终以“截断到当前句”为准。这样读档后就是“停在那句话上”，后面重新生成。

## 二、因此有三件事必须重新定

### ① “继续游戏”怎么办

现在 `auto.json` 是**每轮自动写**的，主菜单“继续游戏”读的就是它。按你新规则“退出即删、没存档就没了”，自动存档就等于自动帮用户存了，冲突。

三个选项：

| 方案 | 行为 |
|---|---|
| A | 取消自动存档，只有手动/快速存档才算（“继续游戏”变成读最近一次手动存档） |
| B | 保留自动存档，但同样截断到当前显示句（= 退出时自动存一次） |
| C | 自动存档只在“到达幕边界”时写一次 |

我倾向 **A**：最符合你说的“没存档就没了”。

### ② 输入框什么时候回来

按你说的：**队列没播完就不出输入框**，必须点完/滚完。那“想提前停”的唯一方式就是退出（丢内容）。

这里有个体验风险：如果导演一口气生成了一幕 20 拍，你看到第 3 拍就烦了，只能连点 17 次或退出。

**建议加一个“放弃未读部分”的确认按钮**（点了才出输入框，未读的丢弃）。不做也行，但我觉得会需要。

### ③ 存档时机

播放中允许存档吗？我建议**允许**，并且存的就是“当前显示的那一句”，和你的规则一致。这样看到一半想留个记录随时能存。

## 三、播放层现在的完整状态机

```
IDLE（输入框显示）
 ├ 玩家发言 / 开自动 → GENERATING
GENERATING（后台生成中，输入框隐藏）
 ├ 队列有内容 → PLAYING
PLAYING（正在演这一句）
 ├ 播完 → 队列有下一条？→ PLAYING（下一句）
 │        队列空？    → IDLE（输入框回来）
 ├ 点击/⏩/滚轮下 → 跳到下一条（按前面定的语音规则）
 └ 关闭自动 → 队列排空？→ IDLE
EXIT → 丢弃队列 + 未存档内容
```

滚轮手势：向下 = 跳过（和点击、⏩ 同一个动作）。

## 需要你确认的三点

1. **自动存档取消（方案 A）还是保留（B/C）？**
2. 要不要那个**“放弃未读部分”**的确认按钮？
3. 播放中**允许存档**吗（存到当前句）？

这三点是最后的冲突点，定完播放层就没有歧义了。
